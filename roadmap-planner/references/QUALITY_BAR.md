# Roadmap Quality Bar

## Strong Roadmap

A strong roadmap:

- gives clear phase order and rationale
- preserves product intent from PRD
- respects architecture constraints
- respects ADR decisions
- avoids one-task implementation detail
- exposes dependencies and risks
- defines exit criteria for each phase
- identifies exactly one next plan candidate
- ends with concrete next step

## Weak Roadmap

A weak roadmap:

- lists features without sequencing logic
- lists tasks instead of outcomes
- hides dependencies
- ignores architecture
- duplicates PRD or ADR content
- invents technical decisions
- creates phases too large to plan from
- omits exit criteria
- says “next: implement roadmap” instead of naming one next plan

## Self-Check

Before final output, verify:

- Is this roadmap based on approved upstream truth?
- Is architecture relevant and included as constraint if needed?
- Are unresolved architecture/ADR questions routed instead of guessed?
- Does each phase explain why it exists now?
- Is there exactly one immediate next step?
